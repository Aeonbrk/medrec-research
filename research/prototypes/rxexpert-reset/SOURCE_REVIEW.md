# Rx-Expert primary-source review

## Source identity

- Official repository: <https://github.com/jhxu003/Rx-Expert> (clone inspected at `/Users/oian/rx-expert-source-review-20260914`).
- Exact `HEAD`: `0750f92cfbf51988d78693ef7797a82ead0ea585` (verified with `git rev-parse HEAD`; `git ls-remote` returned the same SHA for `HEAD`, `main`, and `master` on 2026-09-14).
- Official paper: Jinhang Xu et al., "Mixture of experts based medication recommendation for multimorbidity", *Expert Systems with Applications*, DOI [10.1016/j.eswa.2026.133374](https://doi.org/10.1016/j.eswa.2026.133374), publisher page <https://www.sciencedirect.com/science/article/pii/S0957417426022839>. The publisher abstract says the coarse model uses patient representation plus multimodal molecular representation, patient-specific routing, and a Cross Fusion Module integrating global, substructure, and textual molecular features.

## Coarse-grained mechanism (source-grounded)

- `src/coarse-grained/Rx-Expert.py:141-154`: diagnosis and procedure vocabularies are embedded separately; two GRU expert banks each contain **4** GRUs; two `MoE` layers route the diagnosis and procedure sequences independently.
- `src/coarse-grained/MoE.py:89-225,229-264`: router is learned `Top2Gating`, softmax over **16 gates** because `MoE.num_experts` defaults to 16; each routed slot invokes the supplied four-GRU `GRUExperts` bank. It uses top-2 dispatch, train/eval second-expert policy `random`, thresholds `0.2`, capacity factors `1.25`/`2.0`; balancing loss is returned and scaled by `loss_coef=1e-2` (the supplied GRU-MoE instances omit `num_experts` and therefore retain this 16-gate default).
- `src/coarse-grained/Rx-Expert.py:200-228`: patient representation is built from current-and-prior diagnosis/procedure codes only; the MoE output is converted to a query. Medication codes are not embedded in this pathway. `patient_data=input_seq[:adm_idx+1]` is passed by `src/coarse-grained/training.py:114-117`, so the current visit's diagnosis/procedure are included while its target medication (`adm[2]`) is not.
- `src/coarse-grained/Rx-Expert.py:231-264`: coarse drug path projects a fixed 1024-dimensional text/caption tensor through `Linear(131, substruct_num)` then `Linear(1024, emb_dim)`; GIN graph encoders process molecule and BRICS-substructure SMILES; `SAB` self-attention encodes substructures; `CFM` cross-fuses global graph, substructure, and text features, with `ddi_mask_H` as an attention mask; historical medication sets form a history-value attention fact; a GELU/linear head emits 131 logits.
- `src/coarse-grained/Rx-Expert.py:266-274`: DDI penalty is `0.0005 * (sigmoid(logits)^T sigmoid(logits)).mul(tensor_ddi_adj).sum()`; training combines `0.95*BCE + 0.05*multilabel_margin + MoE auxiliary loss + DDI penalty` (`src/coarse-grained/training.py:121-137`).

## Official coarse configuration

From `src/coarse-grained/main.py`: model dimension/hidden dimension `64` (`:39`, `:134-139`); dropout `0.7` (`:41`, `:120-132`); Adam, LR `5e-4`, no explicit weight decay (`:40`, `:157`); 50 epochs (`:56`, `:158-160`); two four-GRU expert banks behind the default 16-gate Top-2 MoE layers (`Rx-Expert.py:151-154`, `MoE.py:229-264`); GIN, 4 layers, mean pooling, no virtual node (`main.py:119-132`); fixed threshold `sigmoid(logit) >= 0.5` for inference (`training.py:27-36`) and training DDI estimate (`training.py:124-130`). Seeds in the official entrypoint are torch `1203` and NumPy `2048` (`main.py:11-13`), not the screen seed.

The README's provided coarse checkpoint is `src/ckpt/Epoch_38_JA_0.5446_DDI_0.0732.model` (`README.md:47-56`). This is a reference artifact only, not a tuning target. The source also contains the fine-grained checkpoint, but it is out of scope.

## Feature provenance and alignment

- README `:7-13` identifies `smiles_rep.pkl` as features extracted from drug-description information; no upstream encoder/model or extraction script is included. The coarse code assumes this tensor is 1024-dimensional (`Rx-Expert.py:134-136`) and applies it to 131 medication rows (`:131-136,231-232`). This must be treated as a fixed external feature artifact; replacing it with zeros would not be faithful.
- Graph features are generated directly from official `idx2SMILES.pkl` and `substructure_smiles.pkl` via OGB `smiles2graph` (`src/coarse-grained/main.py:82-85,113-128`; `src/coarse-grained/util.py:16-34`). Substructure features are generated by BRICS decomposition (`data/coarse-grained/ddi_mask_H.py:10-35`).
- Official preprocessing maps RxNorm/NDC to ATC level 4 (`data/coarse-grained/processing.py:40-62`), filters to the 300 most common medication codes (`:75-84,374-377`), then builds vocabulary/records and DDI matrix (`:244-273,277-345`). The shipped coarse code assumes 131 medications: `Linear(131, ...)`, output dimension `voc_size[2]`, and utility comment `# 131` (`Rx-Expert.py:131-160,269`; `util.py:291-296`). Therefore the official coarse task is ATC-class/coarse medication semantics and appears dimension-compatible with the canonical 131 output, but exact token-by-token alignment to this project's canonical `voc_final.pkl` was **not performed in this source-only review**; it must be checked before adaptation.
- Official DDI adjacency is built in the official medication-vocabulary order from CID/ATC mappings and filtered side effects (`processing.py:277-345`); `ddi_mask_H` is medication-by-BRICS-fragment (`ddi_mask_H.py:29-35`). Do not assume its order equals the project DDI resource without an explicit mapping check.

## Source-level incompatibilities / adaptation cautions

1. The source repository's filenames/classes use hyphens (`Rx-Expert.py`, `class Rx-Expert`, and `from Rx-Expert import Rx-Expert` in `main.py:8`), which is invalid Python syntax. A faithful adaptation must rename/import mechanically without changing computation.
2. Official `main.py` uses positional patient-record slicing (first 80% train, next half of remainder eval, final half test; `:107-111`), not the project Train/Gate01-Dev patient split. The adaptation must use the project split and must not use the official held-out partition.
3. Official `training.py:61-84` evaluates only the official test partition with repeated random samples; this is not the canonical protocol and must not be copied. The training loop evaluates `data_eval` each epoch and saves every epoch (`:147-183`), so model selection must be defined by the bounded screen without using labels outside Train/Gate01-Dev.
4. The model returns router indices (`Rx-Expert.py:215-216`, `MoE.py:252-264`), but the official code does not persist routing-utilization diagnostics. A screen implementation should instrument these existing indices for the requested diagnostic, without using Dev labels to tune routing.

## Review boundary

No adaptation, training, tuning, or experiment was run. No project data or held-out Audit/test resources were accessed. Findings above are from the official repository at the verified SHA and the publisher abstract/metadata.
